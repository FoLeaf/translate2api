# TransHub 译枢 · 云端翻译网关 — 部署与使用指南

> **TL;DR**：豆包 + B站 Index-Translate 两条翻译线路已经打包成一个 Docker 服务，部署在你的云服务器上，带密码保护的后台、**扫码自动获取 Cookie**（不用再 F12 复制）、可扩展的服务商插件架构。ReadFrog（陪读蛙）里改填两个新地址即可，浏览器侧**零补丁**——你补充的那个 PS1 脚本（删 Origin 头防 412）已经在云端天然实现。

- 服务器：`<服务器IP>`（直连端口 `8301`；域名走 Cloudflare + nginx 反代 + SSL）
- 域名（推荐）：`https://<你的域名>`
- 后台管理：`https://<你的域名>/admin`
- 初始管理员密码：通过 `.env` 的 `ADMIN_PASSWORD` 设置；留空则自动生成随机密码（打印在 docker logs 里，并写入 `data/initial_admin_password.txt`），登录后请到「设置」页改掉
- 项目位置：服务器 `/opt/transhub-go`（本地源码在本仓库 `transhub-go/` 目录）
- nginx 站点：`/etc/nginx/sites-available/<你的域名>`（证书为 Cloudflare Origin CA 泛域名证书，SSE 已关缓冲）

---

## 一、ReadFrog（陪读蛙）怎么填

选项 → API 服务商 → 新增服务商，两个都建：

### 1. 豆包（纯翻译服务商 DeepLX）

| 字段 | 内容 |
|---|---|
| 名称 | `豆包·云端` |
| Base URL | `https://<你的域名>/doubao/{{apiKey}}/translate` |
| API Key | 后台「API Key」页创建的 `th-...`（见下，必填） |

> 为什么 URL 里要带 `{{apiKey}}`：陪读蛙的 DeepLX 服务商不在请求头里携带 API Key，
> 只会把「API Key」字段的值替换进 Base URL 的 `{{apiKey}}` 占位符。网关因此支持从
> URL 路径读取 Key。占位符与 API Key 字段必须同时填，缺一不可。直填
> `https://<你的域名>/doubao/translate` 只适用于会带 `Authorization` 头的客户端
> （curl、其他 DeepLX 前端），在陪读蛙里那样填会得到 401。

### 2. B站 Index（OpenAI 兼容·自定义）

| 字段 | 内容 |
|---|---|
| 名称 | `B站Index·云端` |
| Base URL | `https://<你的域名>/bilibili/v1` |
| API Key | 同一个 `th-...` |
| 模型 | `Index-Translate-2B`（最快，推荐）/ `Index-Translate-9B` / `Index-Translate-35B-A3B` |

> 上游 `/v1/models` 只列出 35B-A3B，但实测 2B 与 9B 同样可用，ReadFrog 里手动输入模型名即可。
> 2026-10 服务器本机流式基准：2B 长文总耗时约 0.78s、首字约 0.43s；9B 约 1.11s、0.42s；
> 35B 约 1.05s、0.56s。要速度选 2B，要质量选 35B。

> 两个地址也支持 IP 直连（`http://<服务器IP>:8301/...`），走域名则是 HTTPS + Cloudflare，更稳更干净。

> 2026-10 起豆包线路入口改为排队消化 + 多段凑批：ReadFrog 请求控制可保持默认（每秒 8、突发 20），网关自动把同批段落合并成少量上游调用并串行限速，防风控由网关统一控制。

## 二、首次使用：两步开通豆包线路

1. **创建 API Key**：后台 → 「API Key」→ 创建，复制 `th-...` 填进 ReadFrog。创建第一个 Key 后，网关立即对公网强制鉴权（之前是完全开放的，别拖）。
2. **扫码登录豆包**：后台 → 「服务商」→ 豆包卡片 → 「开始扫码登录」。页面会实时显示一个浏览器截图（约 1.2 秒刷新），用**豆包 App 的“扫一扫”**扫图里的二维码 → 手机确认 → 3 秒内后台显示“登录成功，Cookie 已自动保存”。豆包线路即刻可用。

B站线路**免登录**，建好服务商就能用（「测试连通」应显示绿色通过）。

### Cookie 过期了怎么办

豆包 Cookie 有效期约 30 天。过期后：后台仪表盘豆包卡片会变红「未就绪」，使用记录里出现 `710012001`——去「服务商」页重新扫一次码即可，流程同上。这就是全部运维量。

## 三、它和你补充的 PS1 脚本的关系

PS1 脚本的原理：给沉浸式翻译的 DNR 规则集注入一条“发请求前删掉 `Origin` 头”的规则，因为 B站网关见到非自家域名的 Origin 就 412。它只适用于 Chromium + 沉浸式翻译。

云端网关把这件事做在了服务端：ReadFrog 的请求先到你的服务器，网关**剥离 Origin/Referer 等头之后**再转发给 `index-translate.bilibili.com`，上游根本看不到扩展 Origin，永不 412。所以：

- Firefox / Chrome / 任何浏览器、ReadFrog / 沉浸式翻译 / 任何 OpenAI 客户端，都无需任何浏览器侧改动；
- 部署时已实测：故意携带 `Origin: chrome-extension://xxx` 请求网关，依然 200 正常出翻译。

## 四、自动获取 Cookie 是怎么实现的（类 OAuth 设计）

- **豆包**：豆包 SSO 的裸 API（`sso.douyin.com/get_qrcode`）已被字节风控 bdms 保护（页面配置明写 `paths.include:["/get_qrcode"]`），纯 API 方案不可行。因此网关在**容器内起一个真实 Chromium** 打开 `accounts.doubao.com`（豆包自建整页登录页，默认展示扫码二维码），截图实时回传后台；扫码确认后页面回跳 doubao.com 落地 Cookie，Playwright 连 HttpOnly Cookie 一起收割入库。浏览器只在扫码的那 5 分钟内存活，平时不占资源。
- **B站**：`passport.bilibili.com` 的 QR API 无风控，纯服务端 generate/poll 实现，后台直接渲染二维码矢量图（当前上游免登录，绑定账号仅作官方收紧时的备用）。
- Cookie 只存在服务器 `/opt/transhub-go/data/transhub-go.db`（SQLite）；旧 Python 库 transhub.db 作为历史存档同目录保留。

## 五、架构：为加服务商留的口子

```
app/
├── gateway.py            # 对外端点：/doubao/translate（DeepLX 协议）、/bilibili/v1（OpenAI 兼容）
├── admin.py              # 后台：页面 + JSON API（登录/扫码/Key/限流/用量）
├── db.py                 # SQLite：settings / credentials / api_keys / usage_log
├── security.py           # scrypt 密码、HMAC 会话、令牌桶限流、登录防爆破
├── providers/            # ★ 服务商插件：@register 自动发现
│   ├── base.py           #   TranslationProvider 抽象（deeplx_translate / openai_proxy 两类协议）
│   ├── doubao.py         #   豆包（SSE 三事件流解析，从本地版适配器移植）
│   └── bilibili.py       #   B站（Origin 剥离 + 流式透传）
└── login/                # ★ 登录流插件：@register_flow 自动发现
    ├── base.py           #   LoginFlow 抽象（start / poll / frame / cancel）
    ├── bilibili_qr.py    #   B站纯 API 扫码
    └── doubao_browser.py #   豆包 Playwright 截图流扫码
```

新增服务商两步：`providers/xxx.py` 实现类 + `@register`；需要登录就再加 `login/xxx.py` + `@register_flow("xxx")`。后台页面和状态接口自动渲染新卡片，不用改任何注册代码。

## 六、常用运维（都在服务器上）

```bash
cd /opt/transhub
docker compose logs -f          # 看日志
docker compose restart          # 重启
docker compose up -d --build    # 升级（改代码后）
tar czf /root/transhub-data.tgz data   # 备份（凭据+Key+用量都在这）
```

- 忘记密码：`docker exec -it transhub python -c "from app import db,security; db.init(); security.set_admin_password('新密码')"`
- 后台已经通过 `https://<你的域名>` 走 TLS（Cloudflare → nginx → 容器，登录 Cookie 自动带 `Secure` 标记），无需再开 SSH 隧道；若 Cloudflare 故障，可临时用 `http://<服务器IP>:8301/admin` 直连应急。
- 豆包线路：入口排队（等待上限 12 秒，超限回 429 并带 Retry-After 头），上游多段凑批（单次最多 8 段或 12000 字符）串行调用，参数经 TH_DOUBAO_QUEUE_WAIT / TH_DOUBAO_QUEUE_CAP 环境变量调整；B站线路：令牌桶 8/秒 突发 16，429 响应带 Retry-After。

## 七、风险与红线

1. 豆包线路仍是逆向非公开接口：**仅供个人使用，禁止商用/批量抓取**，存在风控/失效风险；扫码登录用的是你自己的豆包账号。
2. 所有被翻译文本会经过你的服务器与对应上游，别翻敏感内容。
3. 8301 端口对公网开放，务必保持至少一个 API Key（后台仪表盘会红字提醒）。域名走 Cloudflare（可再叠加 WAF/限速规则），IP 直连 8301 无 CF 防护。
4. B站免费 API 的开放期限未公布，随时可能调整限流或下线；届时后台「测试连通」会变红。
